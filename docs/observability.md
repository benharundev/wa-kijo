# Observability

> **Audience:** customers and operators running wa'kijo in production.
>
> "Observability" here means three things: **logs** (what happened), **traces**
> (how it flowed through the system), and **metrics** (how often, how fast, how
> much). This document explains what wa'kijo emits out of the box and how to
> wire it into your monitoring stack.

---

## 1. Logging

wa'kijo uses [Pino](https://getpino.io) via `nestjs-pino`. Logs are
**JSON-structured** — no string concatenation, no plaintext.

### What gets logged

Every request emits two log entries by default:

```jsonc
// 1. on receipt
{
  "level": 30,                            // info
  "time": 1714638600000,
  "req": {
    "id": "req_7f4a9c5e...",
    "method": "POST",
    "url": "/api/v1/contacts",
    "remoteAddress": "10.0.0.5"
  },
  "msg": "request"
}

// 2. on completion
{
  "level": 30,
  "time": 1714638600045,
  "req": { /* same */ },
  "res": {
    "statusCode": 201,
    "responseTime": 45
  },
  "msg": "request completed"
}
```

Domain code adds structured logs at meaningful events:

```ts
this.logger.info({ workspaceId, contactId, source: 'csv' }, 'Contact created');
```

### Log levels

| Level   | Numeric | Use for                                                   |
| ------- | ------- | --------------------------------------------------------- |
| `fatal` | 60      | Process is about to die. Never recover from these.        |
| `error` | 50      | An operation failed; investigate. Triggers Sentry.        |
| `warn`  | 40      | Something unusual but recovered (rate limit hit, retried) |
| `info`  | 30      | Significant events: requests, jobs, business actions      |
| `debug` | 20      | Dev only; never enable in production for long             |
| `trace` | 10      | Off in production; very noisy                             |

Default `LOG_LEVEL` is `debug` in development and `info` in production.

### What is NOT logged

PII redaction is enforced via Pino's `redact` config and reinforced by code
review. We **never** log:

- Plaintext passwords, tokens, session cookies, or API keys.
- Full email contents or message bodies — log IDs and metadata instead.
- Webhook signing secrets or any value matching `*_SECRET`.
- Phone numbers, except when explicitly required (e.g. webhook delivery audit)
  and after masking the middle digits.

If you find a log statement that violates these rules, treat it as a P1 security
bug.

### Centralised log shipping

Pino writes JSON to stdout. Ship from there using whatever your platform
provides:

| Platform               | Recipe                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| Railway                | Native log aggregation; pipe to Logtail / Better Stack for retention                        |
| Docker Compose VPS     | `docker logs --tail` for ad-hoc; ship to Loki + Grafana, or Vector → Datadog / Better Stack |
| AWS ECS Fargate        | `awslogs` driver to CloudWatch Logs; subscribe a Lambda to forward to your aggregator       |
| Self-hosted Kubernetes | Fluent Bit DaemonSet → Loki / Elasticsearch                                                 |

Filter by `req.id` to follow a single request through the API and worker logs.
The request ID is generated by Fastify and propagated through
`AsyncLocalStorage` to every downstream log line.

## 2. Errors and crash reporting

### Sentry

Set `SENTRY_DSN` to enable Sentry integration on both the API and web. The SDK
is initialised in `apps/api/src/main.ts` (and `apps/web/instrumentation.ts` in
Phase 5).

What we capture:

- All uncaught exceptions (HTTP layer + worker).
- All `error`-level Pino logs (via the Pino-Sentry transport).
- Performance traces for the slowest 5% of requests.

What we **scrub** before sending to Sentry:

- Cookies (the entire `Cookie` request header).
- Authorization headers.
- Anything matching the redaction allow-list above.

### NestJS exception filter

`HttpExceptionFilter` shapes every error into the standard envelope (see
[`api-conventions.md`](api-conventions.md) § 4). It also:

- Logs `error`-level for 5xx responses.
- Logs `warn`-level for 4xx responses.
- Attaches the request ID and active org ID for correlation.

## 3. Tracing (Phase 6+)

OpenTelemetry distributed tracing is on the roadmap for Phase 6. The plan:

- Auto-instrument NestJS HTTP, Prisma, BullMQ, Redis, and outbound HTTP.
- Export to **OTLP** so you can pick the backend (Tempo / Honeycomb / Datadog
  APM / Sentry tracing).
- Trace ID propagated through `AsyncLocalStorage` next to the request ID,
  exposed in every log line.

Until then, request-ID correlation in logs is the primary debugging tool.

## 4. Metrics

### What you can graph today

Pino logs include duration, status code, route, and tenant ID — that gives you
everything you need to compute:

| Metric                             | Source                                        |
| ---------------------------------- | --------------------------------------------- |
| Request rate (RPS, by route)       | Count of `request completed` log entries      |
| Error rate (5xx %, by route)       | Filter `res.statusCode >= 500`                |
| p50 / p95 / p99 latency (by route) | Histogram of `res.responseTime`               |
| BullMQ queue depth                 | `redis-cli llen bull:<queue>:wait`            |
| BullMQ failure rate                | Filter `level=error AND msg='Job failed'`     |
| Active sessions                    | Count of distinct `req.user.id` over a window |

In Grafana / Datadog, set these up as derived log metrics. No code changes
required.

### Dedicated `/metrics` endpoint (Phase 6)

Phase 6 adds a Prometheus-compatible `/metrics` endpoint on the API, guarded by
a `METRICS_TOKEN` query parameter. Until then, derive everything from logs.

## 5. Alerting

A baseline alert pack — every wa'kijo deployment should have these wired up
before going live:

| Alert                              | Trigger                                           | Severity                    |
| ---------------------------------- | ------------------------------------------------- | --------------------------- |
| **API health failing**             | `/api/v1/health` returns non-200 for 2 min        | P1                          |
| **API error rate**                 | 5xx % > 1% over 5 min                             | P1                          |
| **API latency**                    | p95 > 500 ms for 10 min                           | P2                          |
| **Auth failure spike**             | Sign-in 401 rate > 5× the trailing 1-hour average | P2 (possible attack)        |
| **Database connections exhausted** | Postgres `numbackends` > 90% of `max_connections` | P1                          |
| **Database storage**               | Free space < 20%                                  | P2                          |
| **Redis memory**                   | Used memory > 80% of `maxmemory`                  | P2                          |
| **BullMQ queue lag**               | Oldest waiting job age > 5 min                    | P2                          |
| **BullMQ DLQ growth**              | New entry in any DLQ                              | P2                          |
| **Webhook signature failures**     | Rate > 10/min for any provider                    | P2 (config issue or attack) |
| **Email delivery failures**        | Resend `error` rate > 5% over 15 min              | P2                          |
| **Sentry new issue**               | Any new high-severity issue group                 | P3 (creates a ticket)       |

Severity guidance:

- **P1** pages the on-call engineer immediately, 24/7.
- **P2** pages during business hours; otherwise creates a ticket.
- **P3** creates a ticket only.

## 6. Audit logging

Phase 5 introduces `AuditLog` — a Prisma model that records sensitive mutations
(member added/removed, role changed, billing updated, data exported, hard
delete). The schema:

```prisma
model AuditLog {
  id             String   @id @default(cuid())
  organizationId String
  actorUserId    String?
  action         String   // e.g. "member.role.changed"
  entityType     String   // e.g. "member"
  entityId       String
  metadata       Json?
  ipAddress      String?
  userAgent      String?
  createdAt      DateTime @default(now())

  @@index([organizationId, createdAt])
  @@index([actorUserId])
}
```

Audit log entries are **never deleted**. Retention is enforced by partitioning
the table by `createdAt` quarter and dropping old partitions when the
contractual retention window expires (default 7 years for billing-relevant
records, 1 year for everything else).

## 7. Health checks

| Endpoint                             | Purpose                                                                                     | Authenticated? |
| ------------------------------------ | ------------------------------------------------------------------------------------------- | -------------- |
| `GET /api/v1/health`                 | Liveness — process is alive and Postgres + Redis are reachable                              | No             |
| `GET /api/v1/health/ready` (Phase 5) | Readiness — process is warm enough to serve requests (migrations applied, queues consuming) | No             |

Sample health response:

```json
{
  "status": "ok",
  "uptime": 12345.678,
  "checks": {
    "database": { "status": "ok", "latencyMs": 3 },
    "redis": { "status": "ok", "latencyMs": 1 }
  }
}
```

A failing dependency returns HTTP 503 with the same shape so load balancers
remove the instance from rotation automatically.

## 8. Performance debugging playbook

When a request is slow, walk the layers:

1. **Find the request in logs by ID.** Note the `responseTime`.
2. **Check the database.** Was there a slow Prisma query? Enable query logging
   temporarily by setting `DATABASE_LOG=query` and look for queries over 100 ms.
   Add an index or rewrite with `select`.
3. **Check Redis.** A blocking BullMQ producer can stall the request. Producers
   should `add()` and return immediately, never `await` the job.
4. **Check outbound HTTP.** Stripe, Resend, WhatsApp can all stall. Wrap
   external calls in `Promise.race` against a timeout.
5. **Check the worker.** If the slow path involves a job, find the job by ID via
   Bull-Board (`/admin/queues`) and walk the worker logs.

For systemic slowness, run `EXPLAIN ANALYZE` on the suspect query against
production-like data. The output goes in the PR description so reviewers can
sanity-check.

## 9. Useful one-liners

```bash
# Tail API logs filtered by request ID (jq required)
docker compose logs api -f | jq 'select(.req.id == "req_7f4a...")'

# Top 10 slowest endpoints over the last hour (logs in jsonl)
jq 'select(.msg == "request completed") | [.req.url, .res.responseTime]' /var/log/api.jsonl \
  | jq -s 'group_by(.[0]) | map({url: .[0][0], p95: ([.[].[1]] | sort | .[-1])}) | sort_by(.p95) | reverse | .[:10]'

# Postgres top 10 slowest queries (requires pg_stat_statements)
psql -c "SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;"

# Redis memory snapshot
redis-cli info memory | grep used_memory_human

# Live BullMQ queue lag
redis-cli --eval <(echo 'return redis.call("LLEN", KEYS[1])') , bull:message-dispatch:wait
```

## 10. What to monitor first if you're new

If you have one hour to set up monitoring on a fresh deployment, do this in
order:

1. **Sentry** — point `SENTRY_DSN` at a project. Done.
2. **Uptime check** on `/api/v1/health` from an external monitor (Better Uptime,
   Pingdom, or AWS CloudWatch synthetics).
3. **Log retention** — ship stdout somewhere searchable, even if it's just
   `docker logs > /var/log/api.jsonl &`.
4. **Email alerts** for the four P1 alerts in § 5.

The remaining items in § 5 are worth setting up but won't bite you on day one.
